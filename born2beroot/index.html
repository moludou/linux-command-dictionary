実行場所と記号の読み方

基本はDebian VMに一般ユーザーでログインした端末です。SSH接続・ファイル転送は接続元のPCで実行します。各項目に実行場所を記載しています。

evaluationuserは評価用ユーザー名の例、VM_IPは実際の接続先IPへ置き換えます。サービス名・暗号化mapping名・ログ保存先は自分の構成に合わせます。

sudo
後ろの1つのコマンドを、通常root権限で実行します。
|
左の標準出力を右の標準入力へ渡します。
&&
左側が成功したときだけ右側を実行します。
> / >> / 2>
出力を上書き／追記／標準エラーだけ転送します。これはシェルの処理です。
/dev/null
受け取ったデータを保存せず捨てます。
終了状態
通常0が成功、非0が不一致やエラーです。grepの一致なしは1。無表示で成功するコマンドもあります。

一覧は一括実行するスクリプトではありません。必要な項目を選び、表示結果を確認して使います。

コマンドを探す

コマンドを読み込み中です。

apt と aptitude

どちらもDebianのパッケージを管理します。aptはコマンド中心。aptitudeは文字画面でも一覧や変更予定を確認でき、依存関係が競合したときに複数の解決案を比較できます。

目的aptaptitude
検索apt search treeaptitude search tree
詳細apt show treeaptitude show tree
変更予定だけ確認apt install --simulate treeaptitude --simulate install tree
一覧情報の更新sudo apt updatesudo aptitude update
導入sudo apt install treesudo aptitude install tree
削除sudo apt remove treesudo aptitude remove tree
依存関係・why・文字画面の読み方

依存関係は「ソフトを動かすために別のパッケージが必要」という関係です。aptitude why aptitude-commonは、現在のパッケージ情報からその経路をたどります。導入日時や承認した人の履歴ではありません。

why-notは競合する関係を調べます。導入可否を万能に判定するものではなく、変更予定を確認するには--simulateを使います。-yは実際の操作へ自動承諾する指定です。

aptのwhy対応は版によります。apt --versionとその環境のマニュアルで確認します。「whyはaptitudeだけ」とは一般化しません。

引数なしのaptitudeで文字画面を開きます。通常、矢印で移動、Enterで詳細、/で検索、?でヘルプ、qで戻ります。変更を確定する前に対象を確認します。

検索結果の先頭は、i＝導入済み、p＝痕跡なし、c＝設定のみ残存、v＝仮想パッケージ。後ろのAは自動導入です。

aptitudeが未導入で使いたい場合は、sudo apt updateとsudo apt install aptitudeで導入します。これは設定・パッケージを変更する操作です。

ディフェンス：実演コマンドと復元

起動・変更してよい評価用VMで行います。提出署名と照合する元VDIの保全や起動条件は、手元の評価手順書で先に確認します。

各実演は事前確認 → 操作 → 結果確認 → 復元の順です。コマンドは1つずつ実行して結果を読みます。これは添付資料を補強した練習用で、すべてが公式レビューの必須操作という意味ではありません。

一致する実演がありません。検索語を変えてください。

UFW：有効化・無効化・再読込

実行場所：評価用VMのコンソール。SSHだけを操作経路にせず、VM画面から戻せる状態にします。有効化はSSH接続に影響する場合があります。

1. 事前確認

sudo ufw status verbose
sudo ufw show added
sudo ss -lntp

元がactiveかinactiveか、保存済みの許可ルールとSSHの実際の待受ポートを記録します。show addedはUFWで追加済みのルールを表示します。

4242/tcpを許可する構成で、まだ必要な許可がない場合だけ追加します。接続元を限定しているルールがあれば、その範囲を保ちます。

sudo ufw allow 4242/tcp

2. 有効化する

sudo ufw enable
sudo ufw status verbose

enableは保存済みルールを読み込み、現在と起動時のUFWを有効にします。Status: activeと許可ルールを確認します。確認を求められたら影響を読んで判断します。

3. 無効化する

sudo ufw disable
sudo ufw status

disableは現在のUFWによる制御を解除し、起動時も無効にします。Status: inactiveを確認します。保存済みルールを初期化するresetとは違います。

4. 元の状態へ戻す

元がactiveなら次で戻します。

sudo ufw enable
sudo ufw status verbose

元がinactiveならsudo ufw disableへ戻します。追加した4242のルールがあれば、それが今回の追加分か確認して元のルール構成も復元します。現在使うSSHの許可を削除する操作はVMコンソールで行います。課題の通常運用状態はUFW有効です。

補足：有効なUFWのルールを読み直す

sudo ufw reload
sudo ufw status verbose

reloadは再読込です。有効化の代わりではありません。systemctl is-active ufwだけではファイアウォールの有効状態を断定せず、ufw statusで判断します。

説明例：「UFWのenableは現在と起動時の両方を有効にします。disableは両方を無効にします。ルールを消すresetとは区別しています。」

systemctl：今の起動・停止と、自動起動の有効・無効

実行場所：練習用VMのコンソール。例ではcronを使うため、停止中は監視以外のcronジョブも影響を受けます。監視だけを止める実演は下のcrontabの項目を使います。

1. 事前確認

systemctl is-active cron
systemctl is-enabled cron

ここでは元がactive / enabledの場合を実演します。違う場合は記録した状態に合わせて復元します。staticやmaskedの場合に、そのまま同じ操作は行いません。

2. 今の稼働だけを止める・戻す

sudo systemctl stop cron
systemctl is-active cron
systemctl is-enabled cron

inactive / enabledが目安です。stopは今の停止で、自動起動設定は残ります。

sudo systemctl start cron
systemctl is-active cron

startは今の起動です。activeへ戻ったことを確認します。

3. 自動起動だけを無効にする・戻す

sudo systemctl disable cron
systemctl is-enabled cron
systemctl is-active cron

disabled / activeが目安です。disableだけでは今のサービスは停止しません。ほかのunitによる起動まで禁止する指定でもありません。

sudo systemctl enable cron
systemctl is-enabled cron

enableは通常の自動起動設定を戻します。今停止中の場合、これだけでは起動しません。

4. 両方を操作する --now と復元

sudo systemctl disable --now cron
systemctl is-active cron
systemctl is-enabled cron

inactive / disabledを確認後、元がactive / enabledなら次で復元します。

sudo systemctl enable --now cron
systemctl is-active cron
systemctl is-enabled cron

元がactive / disabledならdisableの後にstart、inactive / enabledならenableの後にstop、inactive / disabledならdisable --nowが対応します。状態確認まで行います。

説明例：「start・stopは今の稼働、enable・disableは自動起動の設定です。--nowを付けると現在の起動・停止も一緒に操作します。」

UFW：8080/tcpを追加し、追加分だけ戻す

まずsudo ufw status numberedで8080/tcpの許可が元からないことを確認します。元からある場合、この実演で削除しません。

sudo ufw allow 8080/tcp
sudo ufw status numbered

allowが許可、8080/tcpが対象ポートとプロトコルです。追加したルールを確認後、今回の追加分を戻します。

sudo ufw delete allow 8080/tcp
sudo ufw status verbose
sudo ufw status numbered

8080の追加分が消え、既存の4242の許可とUFWの有効状態が残っていることを確認します。

SSH：設定検査・再読込・接続とroot拒否の確認

1. 事前確認（VM側）

systemctl is-active ssh
systemctl is-enabled ssh
sudo sshd -t
sudo sshd -T | grep -E '^(port|permitrootlogin) '
sudo ss -lntp

sshd -tは正常時無表示です。資料の構成では4242待受とpermitrootlogin noを確認します。Match条件がある場合は接続条件を指定した-T -Cも使います。

2. 設定検査に成功したら再読込

sudo sshd -t && sudo systemctl reload ssh

&&により検査が成功したときだけreloadします。reloadはサービスに設定の読み直しを求め、restartはサービスの停止・起動です。停止や再起動を実演する必要がある場合はVMコンソールで行います。

sudo systemctl restart ssh
systemctl is-active ssh
sudo ss -lntp

3. 別端末から接続確認（接続元PC）

ssh -p 4242 evaluationuser@VM_IP

VM_IPを接続先へ置き換え、ログイン後にwhoamiとidを確認します。一般ユーザーが同じ経路で接続できることを確認してから、root拒否を確かめます。

ssh -p 4242 root@VM_IP

設定のnoとroot認証の拒否を合わせて説明します。Connection refusedやタイムアウトだけではroot拒否の証明になりません。

4. 復元・終了確認

この実演例自体は設定ファイルを書き換えません。編集を伴った場合は事前の設定へ戻し、再度sshd -t成功後にreloadし、新しい接続で確認します。元の接続は確認できるまで残します。socket起動方式の環境はssh.socketも確認し、ssh.service停止だけで接続不能になると決めつけません。

ユーザー：グループ追加・sudo権限の実演と復元

1. 事前確認

getent passwd evaluationuser
getent group evaluating
id evaluationuser

ここでは評価用ユーザーとグループが存在し、追加先へ未所属の場合を実演します。未作成の場合だけsudo adduser evaluationuser、sudo groupadd evaluatingで作成します。元の所属を記録し、操作は元からsudo権限がある管理用ユーザーで行います。

2. 補助グループへ追加

sudo usermod -aG evaluating evaluationuser
sudo usermod -aG sudo evaluationuser

-aは現在の所属を残して追加、-Gは補助グループです。-Gだけでは所属を置き換えます。

3. 登録と実際の権限を確認

id evaluationuser
getent group evaluating
sudo -l -U evaluationuser

評価用ユーザーで再ログインし、idとsudo -lを確認します。許可されていればsudo idでuid=0(root)になることも説明できます。グループ名だけではなくsudoersの実効ルールを確認します。

4. 今回追加した所属だけを戻す

sudo gpasswd -d evaluationuser evaluating
sudo gpasswd -d evaluationuser sudo
id evaluationuser

gpasswd -dは補助メンバーを外す操作です。元からの所属には実行しません。古いログインセッションは所属を保持し得るので終了して再確認します。ユーザー・ホーム自体の削除とは別です。

chage：パスワード期限を設定・確認・復元

1. 事前確認

sudo chage -l evaluationuser

最短日数・最長日数・警告日数の元の値を手元に記録します。ログイン中の管理用ユーザーではなく、評価用ユーザーを対象にします。

2. 資料の値へ設定

sudo chage -m 2 -M 30 -W 7 evaluationuser

-m 2は変更から2日間は通常変更不可、-M 30は30日間有効、-W 7は期限の7日前から警告です。既に最終変更日から30日を超えていれば期限切れになります。

3. 設定結果を確認

sudo chage -l evaluationuser

3項目が2・30・7であることを読みます。文字数・文字種などの強度設定はpwqualityとPAMの役割で、chageでは検査しません。

4. 元の値へ復元

次の日本語部分を、最初に記録した数値へ置き換えます。実演前が2・30・7だった場合はその値へ戻します。

sudo chage -m 元の最短日数 -M 元の最長日数 -W 元の警告日数 evaluationuser
sudo chage -l evaluationuser

期限を無効にする値は-M -1です。元が無期限だったときだけ使用します。復元のために最終変更日やアカウント期限まで変更する必要はありません。

ホスト名：変更・再起動・復元

hostnamectl --staticの結果を元の名前として手元に記録します。バックアップ名が未使用であることを確認して保存します。

sudo cp -ai /etc/hosts /etc/hosts.before-evaluation
sudo hostnamectl set-hostname evaluator42
sudoedit /etc/hosts

sudoeditは管理者権限で対象ファイルを編集するコマンドです。元のホスト名に対応する行だけを新しい名前に合わせ、localhostは残します。確認後にsudo systemctl rebootで再起動し、hostnamectl --staticとcat /etc/hostsを確認します。

復元はsudo hostnamectl set-hostname 元のホスト名（記録した実際の名前に置換）と、次のコピーで行います。

sudo cp -a /etc/hosts.before-evaluation /etc/hosts
sudo systemctl reboot

再起動後に元の名前とhosts内容を確認します。バックアップの整理は復元確認後に行います。

cron：毎分の実演・停止・元の予定表へ復元

最初にsudo crontab -lが成功し、元の予定表があることを確認します。次はバックアップ名が未使用の場合に実行します。シェルのpipefailにより途中の失敗も検出します。

sudo bash -o pipefail -c 'crontab -l | tee /root/crontab.before-monitoring-test >/dev/null'
sudo cat /root/crontab.before-monitoring-test
sudo crontab -e

バックアップ内容が元と一致することを確認してから編集します。監視の行だけを次の形へ変更します。これはcrontabに書く行で、端末へ直接入力するコマンドではありません。

* * * * * /usr/local/bin/monitoring.sh

5個の*は分・時・日・月・曜日の各条件をすべて許可し、毎分実行します。10分ごとは先頭を*/10にします。ユーザーのcrontabには追加のユーザー名欄を書きません。

停止実演ではsudo crontab -eで監視に関係する行の先頭へ#を付けます。@rebootもあれば対象です。ほかのジョブとスクリプト本体は編集しません。

sudo crontab -e
sudo crontab -l
sudo journalctl -u cron -b --since '-3 minutes' --no-pager

編集画面で無効化した行の例（端末への入力ではありません）：

# */10 * * * * /usr/local/bin/monitoring.sh
# @reboot /usr/local/bin/monitoring.sh

保存後、次の予定時刻を過ぎても新しい実行記録や表示が発生しないか確認します。過去の記録は残ります。監視の予定だけを止めるため、ここではcronサービス全体のstopやdisableを使いません。

停止前にsudo sha256sum /usr/local/bin/monitoring.sh | sudo tee /root/monitoring.sha256.beforeで記録すれば、停止・再起動後にsudo sha256sum -c /root/monitoring.sha256.beforeで本体が同じか照合できます。crontabとcronログも確認します。

sudo crontab /root/crontab.before-monitoring-test
sudo crontab -l

復元は予定表全体を置き換えます。実演中に別の変更が入っていないことを確認し、元の10分間隔などへ戻ったことを読みます。

Windows・Rocky Linuxのコマンドはどこで使う？

添付資料のTest-Path・Remove-ItemはWindows PowerShell用です。VBoxManageはVirtualBoxを入れたホストで使用します。VM内のLinuxコマンド一覧には混ぜていません。

dnf・rpm・firewall-cmdはRocky Linuxとの比較用です。このDebian実演ではapt・dpkg・ufwを使います。

提供された「Born2beRoot コマンドリファレンス」「apt と aptitude の違い」「Born2beRoot 評価合格手順書」をもとに構成。値やファイル配置は資料の例です。公式評価票の全項目を保証するものではありません。
